# Plan: Move AI Agent to Rust Backend with rig

## Goal

Move the AI agent system from the frontend (TypeScript/ai-sdk) to the Rust backend using the `rig` crate, remove `ai`/`@ai-sdk/*` from the frontend, and keep the codebase clean.

## Current State

- **Frontend**: All AI logic lives in TypeScript — agent loop (`chat-runtime.ts`), tools (`tools/`), prompts, context management, streaming via ai-sdk `streamText`. Uses `ai` + `@ai-sdk/openai` + `@ai-sdk/anthropic` + `@ai-sdk/openai-compatible`.
- **Rust Backend**: Custom `Provider` trait with 4 implementations (OpenAI, Anthropic, Ollama, Agnes), HTTP proxy (`ai_http_stream`), session/message persistence, security kernel. No agent loop or tools.
- **Key insight**: The Rust backend is currently a "dumb pipe" — all intelligence is in the frontend.

## Design Approach

Use `rig-core` to replace both the custom Rust Provider trait AND the frontend ai-sdk. rig provides:
- Built-in providers: openai, anthropic, ollama, openrouter, deepseek, etc.
- Agent builder with streaming, tools, memory
- Tool trait for defining agent tools
- Pipeline API for multi-step orchestration

### New Architecture

```
User types message
  → Frontend: chat_send_message IPC
    → Rust: rig Agent → stream_chat → Tauri Channel
      → Tool calls require approval? → Channel event → Frontend shows ApprovalCard
      → Tool call approved → Frontend: chat_tool_respond IPC → Rust continues
      → Text deltas → Channel events → Frontend renders
  → Message persisted to SQLite
```

### IPC Contract

```rust
// Send a message — streams events back via Channel
chat_send_message(session_id, content, context_text?) → Ok(())
  // Channel<ChatEvent> events:
  //   TextDelta { content }
  //   ReasoningDelta { content }
  //   ToolCallStart { id, name }
  //   ToolCallDelta { id, args_delta }
  //   ToolCallEnd { id }
  //   ToolApprovalRequired { id, name, args }  // needs user approval
  //   Finish { usage }
  //   Error { message }

// Stop streaming
chat_stop(session_id) → Ok(())

// Respond to tool approval request
chat_tool_respond(request_id, approved) → Ok(())
```

## Implementation Steps

### Phase 1: Rust Agent Core (foundation)

**1.1 Add rig dependency + upgrade reqwest**
- File: `src-tauri/Cargo.toml`
- Add `rig-core = { version = "0.39", features = ["openai", "anthropic", "ollama"] }`
- **Upgrade reqwest from 0.12 to 0.13** (rig-core 0.39 requires reqwest 0.13; API is largely compatible)
- Add `thiserror = "2"` if not already present (rig uses thiserror 2)
- Add `schemars = "1"` for tool JSON schema generation

**1.2 Create agent module structure**
```
src-tauri/src/core/agent/
  mod.rs          — module declarations
  types.rs        — ChatEvent, ChatRequest, ChatResponse types
  engine.rs       — AgentEngine: builds rig Agent, runs streaming chat, handles tools
  tools/          — rig Tool implementations
    mod.rs
    fs_tools.rs   — read_file, list_directory, write_file, create_directory
    edit_tools.rs — edit, multi_edit
    todo_tools.rs — todo_write
  approval.rs     — Tool approval channel (send request, wait for response)
```

**1.3 Implement agent tools as rig Tools**

Each tool implements `rig::tool::Tool`:
- `ReadFileTool` — reads file content (25KB/2000 line cap)
- `ListDirectoryTool` — lists directory contents
- `WriteFileTool` — writes file (requires approval)
- `CreateDirectoryTool` — creates directory (requires approval)
- `EditTool` — single string replace (requires approval + read-before-edit)
- `MultiEditTool` — atomic batch replace (requires approval + read-before-edit)
- `TodoWriteTool` — updates todo list (auto-execute)

Tools requiring approval use `ToolApprovalManager` to:
1. Send `ToolApprovalRequired` event via Channel
2. Wait for `chat_tool_respond` IPC call
3. Return result or error based on approval

**1.4 Implement AgentEngine**
- `AgentEngine::new()` — creates engine with rig provider from config
- `AgentEngine::send_message()` — builds rig Agent with tools + system prompt, runs streaming chat, sends events via Channel
- `AgentEngine::stop()` — cancels streaming
- `AgentEngine::respond_approval()` — resolves pending tool approval
- Session management: load history from DB, persist messages after completion

**1.5 Create IPC commands**
- File: `src-tauri/src/core/agent/commands.rs`
- Register in `lib.rs`

### Phase 2: Frontend Cleanup

**2.1 Remove AI SDK dependencies**
- Remove from `package.json`: `ai`, `@ai-sdk/openai`, `@ai-sdk/anthropic`, `@ai-sdk/openai-compatible`
- Remove `zod` if only used for AI tool schemas (check — it's used elsewhere too, keep it)

**2.2 Simplify chat runtime**
- Replace `src/features/agent/services/llm/` (all of it) with thin IPC wrapper
- New `chat-runtime.ts`: just calls `chat_send_message` IPC and listens to Channel events
- Remove: `resolve-model.ts`, `compact.ts`, `apply-cache-breakpoints.ts`, `proxy-fetch.ts`
- Keep: `stream-protocol.ts` (pure reducer, still useful for frontend state)

**2.3 Simplify tools**
- Remove `src/features/agent/services/tools/` entirely (tools now live in Rust)
- Remove security.ts (path/command security now in Rust tools)
- Keep `plan-store.ts` (plan mode is UI concern — but modify: plan mode flag sent to Rust via IPC)

**2.4 Update chat hook**
- `useChat.ts`: calls new IPC instead of `sendMessage` from chat-runtime
- Approval flow: receives `ToolApprovalRequired` events, shows ApprovalCard, calls `chat_tool_respond`

**2.5 Remove dead code**
- `src/features/agent/services/agents/` — all BaseAgent subclasses (architect, writer, polisher, etc.) — these are pipeline agents. Keep prompt files, remove runtime code for now (pipeline migration is separate)
- `src/features/agent/services/subagent/` — subagent system (move to Rust in Phase 3)
- `src/features/agent/services/llm/` — entire directory
- `src/features/agent/services/approval.ts` — replaced by Rust-side approval
- `src/features/agent/services/security.ts` — replaced by Rust-side tool security
- `src/features/agent/services/project-memory.ts` — move to Rust

### Phase 3: Provider Migration

**3.1 Replace custom Provider trait**
- Remove `src-tauri/src/infrastructure/llm/` (custom provider implementations)
- Use rig's built-in providers directly
- Keep `registry.rs` concept but adapt to rig: `ProviderRegistry` builds rig Clients from config

**3.2 Remove ai_http_stream / ai_http_request**
- These were proxy commands for frontend ai-sdk. No longer needed.
- Keep `lm_ping` for connectivity testing.

- Subagent system — migrate to rig subagents later
- Context compaction — can add later as rig middleware
- Anthropic cache breakpoints — rig handles this natively
